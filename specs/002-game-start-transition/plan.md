# Implementation Plan: Game Start Transition

## Summary

Scenario 2 adds the game-start lifecycle on top of the completed Scenario 1 lobby. When the
host clicks "Start Game", a `POST /rooms/:code/start` call transitions the room from `"lobby"`
to `"playing"`, assigns a drawer (host preferred), and selects a secret word. A new
`GET /rooms/:code/game` endpoint returns a `GameSnapshot` — conditionally including `secretWord`
only for the drawer. Non-host players auto-transition to the game screen via the existing
~2s lobby poll. The frontend gains a dedicated `gameStore` and the `GamePage` switches from
placeholder data to live game state. All Scenario 1 flows are untouched.

## Technical Context

**Language/Version**: TypeScript (strict), Node.js 18+, React 18

**Primary Dependencies**: Express, Zod (backend validation), React Router v6, `tsx` (dev)

**Storage**: In-memory only — `Map<string, Room>` in `roomStore.ts`. No external store.

**Testing**: Vitest (backend unit tests). Frontend: manual two-tab validation via `quickstart.md`.

**Target Platform**: Local development server — `localhost:3001` (backend), `localhost:5173` (frontend)

**Project Type**: Monorepo web application (Express backend + React/Vite frontend)

**Performance Goals**: Polling at ~2s; start-game endpoint must respond within standard HTTP latency (<200ms locally)

**Constraints**: No WebSockets, no databases, no authentication, no Scenario 3 logic

**Scale/Scope**: Single in-memory server, 2–8 players per room, 5-word starter list

## Implementation Sequence

The steps below are strictly ordered within each phase. See `tasks.md` for full task breakdown.

### Phase A — Backend Model (strictly sequential)

1. `game.ts`: Widen `RoomStatus` to `"lobby" | "playing"`; add `Round` interface;
   add `currentRound: Round | null` to `Room`; add `GameSnapshotBase`, `DrawerGameSnapshot`,
   `GuesserGameSnapshot`, `GameSnapshot` types.

2. `roomStore.ts` (backend): Add `startGame(code, participantId)` function implementing the
   drawer assignment rule and word selection. Add `toGameSnapshot(room, viewerParticipantId?)`.

3. `schemas.ts`: Add `startRoomSchema` (requires `participantId`) and `gameViewerQuerySchema`.

4. `rooms.ts`: Add `POST /:code/start` and `GET /:code/game` route handlers.

**Checkpoint**: `cd backend && npm run build` → zero errors.

### Phase B — Backend Tests (can run after Phase A)

5. `roomStore.test.ts`: Add tests for `startGame` — happy path, 403 non-host, 400 <2 players,
   409 already playing, drawer assignment (host present / host absent), word from list.

6. `schemas.test.ts`: Add tests for `startRoomSchema` — missing `participantId`, blank `participantId`.

**Checkpoint**: `cd backend && npm test` → all tests pass.

### Phase C — Frontend Types (parallel with Phase B after Phase A)

7. `api.ts`: Widen `RoomSnapshot.status`; add `GameSnapshot` type; add `startGame()` and
   `fetchGameState()` API methods.

### Phase D — Frontend State (after Phase C)

8. `gameStore.ts` (new): Implement `GameState`, `GameStore` class with `setGameSession`,
   `fetchGame`, `reset`; export `GameStoreProvider`, `useGameStore`, `useGameState`.

9. Update app root to wrap `GameStoreProvider` around routes (alongside existing `RoomStoreProvider`).

### Phase E — Frontend Pages (after Phase D; sequential on LobbyPage, then GamePage)

10. `LobbyPage.tsx`: Replace `onClick={() => navigate("/game")}` with `handleStartGame` that
    calls `api.startGame`, stores result in `gameStore`, then navigates. Add status-check in
    poll callback to redirect non-hosts when `status === "playing"`.

11. `GamePage.tsx`: Replace `useRoomState()` with `useGameState()`; add `setInterval` poll
    calling `gameStore.fetchGame()` every 2s; derive `isDrawer`; render drawer banner
    (`secretWord`) or guesser placeholder conditionally.

**Checkpoint**: `cd frontend && npm run build` → zero errors.

### Phase F — Polish & Validation

12. Run `npm test` in `backend/` — all tests green.
13. Manual two-tab validation per `quickstart.md` Steps 1–10.

## Key Design Constraints (implementation reminders)

- `secretWord` MUST only appear inside `toGameSnapshot` when `viewerParticipantId === drawerId`.
  It must never be added to `toRoomSnapshot` or any shared snapshot.
- The host check in `POST /:code/start` MUST happen **before** the `startGame` service call
  (in the route handler via Zod + explicit comparison, not inside the service — keep service pure).
  Actually: the spec places the 403 guard within `startGame` for simplicity. The route handles
  Zod validation (400 for missing field); the service handles the identity check (403).
- `Room.currentRound` initializes as `null` in `createRoom`. The TypeScript type enforces this.
- The `LobbyPage` Start Game handler must catch errors and display inline error — do not let
  failed start calls navigate or leave the lobby in a broken state.
- `GamePage` must guard: if `gameStore.game` is `null`, redirect to `/` (user landed directly
  on `/game` without going through lobby).
