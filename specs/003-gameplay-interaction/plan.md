# Implementation Plan: Gameplay Interaction

**Branch**: `003-gameplay-interaction` | **Date**: 2026-06-01 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/003-gameplay-interaction/spec.md`

## Summary

Scenario 3 adds the interactive gameplay layer on top of the Scenario 2 playing state:
the drawer draws on an HTML5 canvas (strokes synced server-side and polled by guessers),
guessers submit validated text guesses that are scored case-insensitively (100 points,
capped at one scoring event per participant per round), and all players see shared guess
history and a live scoreboard via the existing ~2s `GET /rooms/:code/game` polling.

Three new backend endpoints are introduced (`POST /canvas/stroke`, `DELETE /canvas`,
`POST /guess`). The `Round` model, `GameSnapshot`, and four frontend components are extended
additively. No Scenario 1 or 2 behavior is modified.

## Technical Context

**Language/Version**: TypeScript (strict), Node.js 18+ (backend), React 18 (frontend)

**Primary Dependencies**: Express + Zod (backend); React Router v6, Vite (frontend);
`useSyncExternalStore` pattern (state management — follows existing `gameStore.ts`)

**Storage**: In-memory only (`Map<string, Room>` — no databases per constitution)

**Testing**: Vitest (backend unit tests; `npm test` in `backend/`)

**Target Platform**: Local dev server (`localhost:3001` backend, `localhost:5173` frontend)

**Project Type**: Brownfield web application enhancement (monorepo)

**Performance Goals**: All three new endpoints respond within the same synchronous
in-memory latency as existing endpoints (~1ms). No explicit throughput targets for a
single-room dev lab.

**Constraints**: No WebSockets, no persistence, no authentication, no new routing or
state-management libraries, no third-party drawing libraries. All per the constitution.

**Scale/Scope**: Single in-memory room; 2–N players; one active round at a time.

## Key Design Constraints

1. **Additive only**: `Round`, `GameSnapshotBase`, `startGame`, `toGameSnapshot` are
   extended, not rewritten. All Scenario 2 callers continue to work unchanged.

2. **Single polling response**: `strokes`, `guesses`, and `scores` are returned in the
   existing `GET /rooms/:code/game` response — no new polling endpoint.

3. **Immediate feedback on guess**: `POST /rooms/:code/guess` returns `{ game: GameSnapshot }`
   so the guesser's store is updated immediately; polling still serves all other players.

4. **Scoring cap enforced server-side**: `submitGuess` checks `scores[participantId] === 0`
   before incrementing. The frontend renders scores from the server — no client-side
   score arithmetic.

5. **Canvas replay model**: The client replays `strokes` from the beginning on every render.
   This is stateless from the guesser's perspective — they never accumulate local state.

6. **No Scenario 4 concepts**: No end-of-round detection, no result state, no restart.
   The round remains active indefinitely in Scenario 3.
