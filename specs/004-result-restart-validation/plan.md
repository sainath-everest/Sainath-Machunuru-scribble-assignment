# Implementation Plan: Result, Restart & Final Validation

**Branch**: `SainathM/assignment` | **Date**: 2026-06-02 | **Spec**: [spec.md](spec.md)

## Summary

Scenario 4 closes the game lifecycle: the host manually ends an active round (transitioning
the room to a new `"result"` status), all participants see a result screen showing the secret
word, final scores, and full guess history via the existing `GET /rooms/:code/game` polling
endpoint (which is extended to serve the result snapshot). The host then triggers a restart
that returns the room to `"lobby"` status with participants preserved and all round state
cleared. Non-host players are redirected automatically when their game poll returns a 409
(round gone) after having been in result state.

Two new backend service functions (`endRound`, `restartGame`), two new Zod schemas, two new
routes, and one type extension drive the backend. The frontend gains a new `ResultScreen`
component, a `roundEnded` redirect flag in `GameStore`, and two new API/store methods. No
Scenario 1, 2, or 3 code is altered in behavior.

## Technical Context

**Language/Version**: TypeScript (strict), Node.js 18+ (backend), React 18 (frontend)

**Primary Dependencies**: Express + Zod (backend); React Router v6, Vite (frontend);
`useSyncExternalStore` pattern (state management — follows existing `gameStore.ts`)

**Storage**: In-memory only (`Map<string, Room>` — no databases per constitution)

**Testing**: Vitest (backend unit tests; `npm test` in `backend/`)

**Target Platform**: Local dev server (`localhost:3001` backend, `localhost:5173` frontend)

**Project Type**: Brownfield web application enhancement (monorepo)

**Performance Goals**: `endRound` and `restartGame` are synchronous in-memory operations —
same sub-millisecond latency as all existing service functions.

**Constraints**: No WebSockets, no persistence, no authentication, no new routing or
state-management libraries, no third-party component libraries. All per the constitution.

**Scale/Scope**: Single in-memory room; 2–N players; one active round at a time.

- `room.participants` is untouched — all players preserved.

`T010` — `restartGame` tests:

## Key Design Constraints

1. **Additive only for Scenarios 1–3**: `RoomStatus`, `GameSnapshotBase`, `toGameSnapshot`,
   `GET /:code/game` are extended, not rewritten. All Scenario 1/2/3 callers continue to
   work unchanged. The single-line guard change in `GET /:code/game` is the only modification
   to an existing route.

2. **`currentRound` preserved during result state**: Round data is NOT copied to a new field.
   `currentRound` is populated in both `"playing"` and `"result"` statuses. It is set to
   `null` only in `restartGame`. This keeps `toGameSnapshot` as the single serialization
   function.

3. **Same polling endpoint for result state**: `GET /rooms/:code/game` serves both `"playing"`
   and `"result"` snapshots. No new polling loop is introduced. After restart, the same
   endpoint returns 409 again — the frontend uses this as the redirect signal.

4. **`roundEnded` flag scoped to post-result 409**: The redirect is gated on
   `game.status === "result"` at the time the 409 arrives. This prevents false redirects
   during initial game load (where 409 means "game not started" and users should stay on the
   lobby/start page, not navigate away from a valid game page).

5. **No changes to Scenario 3 guard behavior**: `addStroke`, `clearCanvas`, and `submitGuess`
   already guard `room.status !== "playing"`. When status is `"result"`, they return
   `409 "Game has not started yet"` — correct behavior, zero code change needed.

6. **Host identity from `room.hostId`**: `isHost` is derived client-side by comparing the
   locally stored `participantId` to `room.hostId` from the room snapshot. No server-side
   session or token is used — consistent with the no-auth constitution constraint.
